## Why

조회 결과와 자동완성 인덱스가 모두 60초에 만료되고, 경기 댓글 수정이나 업로드 예약까지 전체 캐시를 무효화하므로 요청 간격이 긴 서비스에서 재사용 효과가 작다. 현재 60초 TTL은 Redis 무효화 실패의 안전장치이기도 하므로, 변경 버전의 신뢰성을 확보한 뒤 데이터별 보관 시간을 늘려야 한다.

## What Changes

- 인증·버전 확인·Redis·업무 DB 조회·인덱스 게시 시간을 분리해 측정한다.
- PostgreSQL 업무 트랜잭션에 범위별 변경 버전을 함께 기록하고, 인증된 읽기에서 현재 버전으로 Redis 키를 구성한다. Redis 쓰기 실패가 장시간의 오래된 결과 노출로 이어지지 않게 한다.
- 전체 generation을 모임원, 계정, 경기 목록, 개별 경기, 전적, Riot 검색 자격 범위로 나눈다. 업로드 예약과 감사 기록만으로는 업무 캐시를 무효화하지 않는다.
- 버전 검증이 적용된 캐시에 정책별 TTL을 도입한다. 모임원 목록은 연결 계정 정보를 포함해 정확히 24시간(86,400초), 경기 목록은 30분, 경기 상세·자동완성은 6시간, 전적 집계는 1시간, 전적 페이지는 30분 보관한다.
- 일반 조회의 동일 키 동시 로딩을 합치고, 자동완성에는 인스턴스 간 재구축 조정과 제한된 대기를 도입한다.
- 전적 집계와 페이지 결과를 분리하고, Redis 왕복·게시 비용과 캐시 키 증가를 줄인다.
- 현재 구현된 10경기 참가자 목록과 `game-list-v2`·`game-detail-v2`·`member-history-v2` 투영을 보존한다. 경기 목록에는 모임원·계정 revision을 필수로 포함하고 기존 페이지 단위 참가자 일괄 조회를 재사용한다.
- 이미 구현된 24시간 챔피언/패치별 에셋 캐시는 보존하고, Redis 조회 이후의 카탈로그 조회·이미지 로딩 비용을 분리해 검증한다.
- 기존 권한 검사, 역할별 투영, 검색 URL/DTO, 원자적 인덱스 게시, 장애 시 DB 조회를 유지한다.

## Capabilities

### New Capabilities

- `cache-revision-consistency`: 업무 변경과 원자적으로 저장되는 범위별 버전, 현재 버전 확인, 배포 전환과 실패 시 캐시 우회.

### Modified Capabilities

- `query-cache`: 데이터별 만료 정책, 범위별 버전 키, 동시 로딩 공유, 캐시 사용량과 성능 검증.
- `member-name-search`: 장기 보관하는 자동완성 스냅샷, 소스별 변경 범위, 여러 인스턴스의 재구축 조정.

## Impact

`query-cache.ts`, `autocomplete-index.ts`, `read-model.ts`, `member-history.ts`, `nickname-search.ts`, `redis.ts`, `audit.ts`, 회원·경기 mutation 및 `ingest.ts`, DB 스키마와 migration, Redis/PostgreSQL 통합 테스트, 운영 문서가 대상이다. DB 버전 테이블을 추가하지만 기존 공개 URL과 응답 DTO는 유지한다. 새 외부 서비스는 필요하지 않다.

이 변경은 2026-10-15 현재 작업 트리를 바탕으로 작성하고 추가 UI·조회 변경까지 재검토한 **계획**이다. 완료된 경기 목록 참가자 표시, 전적 카드와 상세 아이템 투영을 의존 범위에 반영했다. Redis 개선의 애플리케이션 구현, migration 실행, 운영 성능 측정과 배포는 아직 수행하지 않았다.
