## Context

LLVY는 Next.js 16 App Router, Server Actions와 Proxy를 사용한다. 현재 `UPLOAD_PASSWORD` 하나로 로그인하고, 역할 없는 HMAC 서명 세션을 30일 동안 사용한다. 관리·경기 변경 Action은 `assertSession()`만 호출한다. 모임원 명부와 라이엇 계정 연결은 관리 Action에서 변경하며, 리플레이 수집은 미연결 계정 생성과 기존 계정의 표시 이름 갱신 및 경기 저장을 수행한다.

이미 작업 트리에 요청 제한·업로드 정리 등의 변경이 있다. 이 변경은 그 구현 위에 적용하며 기존 변경을 되돌리지 않는다. 저장소에 확정된 `openspec/specs/`는 없으므로 역할 정책을 새 capability로 기술한다.

## Goals / Non-Goals

**Goals:**

- 두 공유 키로 업로더와 관리자 역할을 구분하고 서버에서 권한 경계를 강제한다.
- 기존 업로드·조회 흐름과 로그인 IP 제한, 세션별 업로드 예산을 보존한다.
- 역할·만료 시각·세션 식별자를 서명하고 키 교체에 따른 세션 폐기를 보장한다.
- 화면과 운영 문서에 실제 권한을 일관되게 반영한다.

**Non-Goals:**

- 개인 로그인, 개인별 키나 업로드 소유권, 사용자별 감사 로그, OAuth 도입.
- DB 모델 변경, 업로드 처리·유지보수 인증 정책 변경, 운영 환경변수 변경·배포.
- 업로드에 수반되는 계정 자동 생성·표시 이름 갱신·전적 갱신을 금지하는 DB 전체 읽기 전용 정책. 업로더의 RO는 모임원 명부와 수동 관리 기능에 적용한다.

## Decisions

### 1. 역할과 기능 행렬

| 기능 | uploader | admin |
| --- | --- | --- |
| 업로드 예약·Blob 업로드·리플레이 처리 | 허용 | 허용 |
| 경기 목록·상세·제외된 경기, 모임원 목록·상세·통계 조회 | 허용 | 허용 |
| 모임원 생성·이름·생년 수정 | 거부 | 허용 |
| 라이엇 계정 연결·연결 해제 | 거부 | 허용 |
| 경기 날짜 수정·원본 복원·제외·복구 | 거부 | 허용 |
| `/admin` 및 하위 경로 | 거부 | 허용 |

관리자에게 업로더 기능을 포함시켜 키를 바꿔 로그인할 필요가 없게 한다. 모임원 연결과 경기 보정은 과거 통계에도 영향을 주므로 관리자에게 제한한다. 업로드 시 발견된 계정은 기존대로 미연결 상태로 생성하고 수동 연결은 관리자가 결정한다.

### 2. 단일 로그인과 설정 검증

`UPLOAD_PASSWORD`는 기존 값 그대로 업로더에게 배포한다. `ADMIN_PASSWORD`는 관리자만 공유한다. 로그인 입력은 하나이며 서버의 `authenticatePassword()`가 `uploader | admin | null`을 반환한다. 클라이언트가 전달한 역할은 사용하지 않는다. 잘못된 키는 역할별 정보를 노출하지 않는 동일한 오류와 기존 400ms 지연을 사용한다. 두 키는 같은 IP별 로그인 예산을 소비하고 예산 검사가 키 비교보다 먼저 실행된다.

두 로그인 키는 비어 있거나 공백만 있어서는 안 되며 서로 달라야 한다. `AUTH_SECRET`은 앞뒤 공백 제거 후 UTF-8 기준 32바이트 이상이고 두 로그인 키와 달라야 한다. 누락·중복·짧은 비밀값은 구성 오류로 처리하고 비밀값을 오류에 포함하지 않는다. 구성 오류에서는 세션을 생성하지 않고, 세션 검증도 실패한다. 로그인 화면에는 일반적인 설정 오류를 반환한다. `AUTH_SECRET`에는 `openssl rand -base64 32`로 생성한 독립적인 난수를 사용한다.

로그인 비밀번호를 서명 비밀값으로 사용하는 기존 fallback은 제거한다. 역할별 공유키 보유자가 서명키를 계산할 수 있으면 역할 경계를 우회할 수 있기 때문이다. 관리자 키를 서명키로 재사용하는 대안도 비밀값의 배포 범위를 혼동하므로 사용하지 않는다.

### 3. 역할이 서명된 v3 세션

세션 형식은 `v3.<role>.<issuedAtMs>.<uuidNonce>.<base64urlHmac>`이다. 원문에는 비밀번호와 서명 비밀값을 포함하지 않는다. 서명은 전체 payload를 보호하고 역할은 `uploader`와 `admin`만 인정한다. 버전·필드 수·역할·정수 시각·UUID 형식·서명의 정규 base64url 형식·최대 토큰 길이를 검사한다. 같은 서명의 비정규 base64 표현은 거부하여 세션별 업로드 예산 식별자를 하나로 유지한다. 기존 30일 유효기간과 최대 60초 미래 시각 허용을 유지한다. 기존 v1/v2 세션은 서명과 무관하게 거부한다.

HKDF의 IKM은 서버의 `AUTH_SECRET`, salt는 `JSON.stringify(["llvy-session-hkdf-v3", role, 해당 역할의 현재 로그인 키])`, info는 `llvy-session-hmac`이다. HMAC SHA-256 키를 역할별로 파생한다. 따라서 역할 변조·다른 역할의 키로 서명한 토큰을 거부하고 각 역할의 로그인 키 교체 시 해당 세션만 무효화한다. `AUTH_SECRET` 교체는 모든 역할을 무효화한다. 파생키 캐시는 역할별 최근 설정 한 개씩만 보관한다.

`readSessionToken()`은 검증된 `{role, issuedAt}` 또는 null을 반환한다. 기존 업로드 호출부를 위해 `verifySessionToken()`의 boolean 계약을 유지한다. 서버의 `getSession()`은 검증된 역할과 원래 토큰을 반환하여 업로드 예산 식별자를 보존한다. `assertAdmin()`은 미인증과 업로더의 권한 부족을 별도 오류로 구분한다.

DB 세션을 도입하는 대안은 개인별 폐기에는 유리하지만 현재 두 공유 키에는 불필요하다. 환경변수에 연결된 역할별 세션 폐기로 요구사항을 충족한다.

### 4. 서버 인가와 화면

Proxy는 미인증 API에 401, 페이지에 기존 로그인 redirect를 유지한다. 업로더의 `/admin`·하위 경로 접근은 `/members`로 이동시킨다. 관리 페이지는 자체 세션·역할 검사 후 조회하여 Proxy를 거치지 않은 호출도 차단한다. 권한 검사는 레이아웃이나 경로 검사에만 의존하지 않는다.

네 개 모임원 변경 Action과 세 개 경기 관리 Action은 입력 처리·DB 쓰기 전에 `assertAdmin()`을 호출한다. 미인증에는 재로그인 안내, 유효한 업로더 세션에는 관리자 권한 필요 안내를 반환하며 DB 쓰기와 캐시 무효화를 수행하지 않는다. 이는 Server Action의 상태 응답이며 새 관리자 HTTP API는 추가하지 않는다.

내비게이션은 현재 역할을 표시하고 업로더에게 관리 링크를 숨긴다. 모임원 목록·상세의 관리 바로가기와 빈 목록의 추가 링크, 계정 중복 연결의 관리 링크도 관리자에게만 표시한다. 업로더는 중복 연결 확인 필요 안내를 읽을 수 있다. 경기 상세의 날짜 수정·복원·제외·복구 폼과 제외 경기 목록의 복구 폼도 관리자에게만 표시한다. 모임원 조회는 기존 `/members`를 사용한다. 제외된 경기 조회는 읽기 기능이므로 두 역할에 허용한다. 로그인 redirectTo가 관리자 경로이면 업로더는 `/members`로 이동한다. 잘못된 redirectTo의 기존 내부 URL 정규화는 유지한다.

### 5. 회귀 검증

- 실제 서명·검증으로 역할 변조, 기존 버전, 만료·미래 시각, 설정 오류, 양쪽 키 및 서명 비밀값 교체를 확인한다.
- 실제 세션과 쿠키를 사용한 테스트에서 모든 관리 Action의 직접 호출이 업로더·미인증·변조 세션을 차단하고 DB 쓰기와 캐시 무효화가 없는지 확인한다. 관리자 호출은 허용한다.
- Proxy·관리 페이지·로그인 Action과 역할별 내비게이션·경기 폼 표시를 검증한다. 업로드 경로는 두 역할의 실제 세션 검증과 기존 API·DB 테스트를 함께 사용한다.
- `openspec validate add-uploader-admin-roles --strict`와 `npm run check`를 통과시킨다. 브라우저에서 두 역할의 조회·폼 표시·관리 경로 이동을 로컬로 확인하되 운영 검증으로 보고하지 않는다.

## Risks / Trade-offs

- [공유키 사용자별 식별·폐기 불가] → 역할 키 교체로 해당 역할 전체를 로그아웃한다. 개인별 관리가 필요하면 별도 계정 체계를 설계한다.
- [잘못된 설정으로 로그인 불가] → `.env.example`과 배포 안내에 필수값·서로 다른 키·서명 비밀값 조건을 명시하고 로그인 시 비밀값을 포함하지 않는 설정 오류를 표시한다.
- [오래 열린 화면에 관리 폼이 남을 수 있음] → 서버 Action은 매번 현재 쿠키와 설정으로 검증하고 UI는 권한 경계로 사용하지 않는다.
- [기존 세션으로 진행 중인 업로드가 중단됨] → 배포 시 재로그인 안내 후 새 업로드를 시작한다. 기존 바인딩은 유지하고 만료 정리 작업으로 처리한다.
- [업로더가 리플레이를 추가하면 조회 정보도 갱신됨] → 업로드로 인한 경기·계정 수집은 허용한다. 모임원의 이름·생년·계정 소속을 직접 바꾸는 수동 관리는 차단한다.

## Migration Plan

1. 환경별로 기존 `UPLOAD_PASSWORD`를 유지하고 별도의 `ADMIN_PASSWORD`, 독립적인 32바이트 이상 `AUTH_SECRET`을 설정한다. 관리자 키와 서명 비밀값을 업로더에게 배포하지 않는다.
2. Preview에서 새 앱과 두 키로 권한 행렬·직접 관리 요청 거부·업로드·키 교체를 확인한다. DB 마이그레이션은 이 변경에 필요하지 않다.
3. 환경변수와 앱을 함께 배포한다. 기존 세션은 모두 거부되므로 재로그인한다.
4. 롤백 시 이전 앱은 모든 로그인 사용자에게 관리 권한을 주므로 접근을 운영자에게 제한하고 공유키·서명 비밀값을 새 값으로 교체한다. 이전 공유키 권한으로의 롤백은 역할 분리 보장을 제공하지 않는다.
