## Context

`add-go-windows-replay-uploader`는 61개 미완료 작업과 7개 델타 명세를 가진 계획이다. 웹 런타임은 변경하지 않고, 서버 계획은 LLVY에 남기며 앱 계획과 독립 릴리스 책임을 형제 저장소로 옮긴다.

## Goals / Non-Goals

**Goals:** 저장소별 OpenSpec, 단일 API 계약 원본, 기존 리뷰·작업·시나리오 추적, 확장 프로젝트용 위키 탐색.

**Non-Goals:** Go 뼈대나 서버 API 구현, 실제 기능 플래그 추가, DB 변경, CI 실행·배포·원격 저장소 발행.

## Decisions

### 저장소와 계획 분리

LLVY의 활성 변경 이름은 `add-desktop-replay-upload-api`, 새 저장소의 앱 변경은 `add-go-windows-replay-uploader`로 한다. Windows UI·탐색·배포 명세는 앱으로 이동하고 인증·업로드 공개 계약과 기존 웹 명세 변경은 서버에 남긴다. 공개 계약이 정의하는 클라이언트 준수 조건은 계약 원본의 일부이며, 앱은 이를 참조한다. Windows 자격 증명 저장 구현은 앱 명세로 옮긴다.

같은 저장소에서 경로 필터로 배포를 나누는 기존 선택은 독립 저장소와 버전 계약으로 대체한다. 실제 앱 코드가 없으므로 Go 버전·모듈 경로·CI를 임의로 확정하지 않는다.

### 계약 소유권과 독립 실행

LLVY의 `contracts/desktop-v1/`가 향후 기계 판독 계약·fixture의 원본이다. 지금은 관리 절차만 둔다. 앱은 구현 시 원본 commit과 체크섬을 기록한 계약 사본을 자체 저장소에 포함해 단독으로 빌드·검증한다. 형제 경로 import·submodule·부동 최신 버전 다운로드를 빌드 전제로 삼지 않는다. 배포된 exe의 v1 호환성을 지키며 서버 호환 배포 후 앱을 발행한다.

업로더는 LLVY API와 서버가 승인한 Blob 전송에 연결한다. Worker·QStash는 업로더의 의존성이 아니다. `DESKTOP_UPLOADER_ENABLED` 기본 false는 서버 구현 계획으로 유지하며 Worker 연동 설정과 분리한다.

### 이력과 완료 상태

기존 원본은 앱의 `docs/history/2026-10-18-monorepo-plan/`에 비활성 이력으로 보존한다. 새 작업 목록은 기존 번호를 유지하고 양쪽에 필요한 검증은 각 저장소의 책임으로 나눈다. 61개 번호의 목적지 표를 제공한다. 기존 리뷰는 과거 계획 검토 기록으로 링크하고 이번 분리 검증과 구분한다.

이번 관리 변경만 완료 후 아카이브한다. 기능 구현 변경 두 개는 미완료로 유지하고 계획을 정식 구현 명세로 승격하지 않는다.

## Risks / Trade-offs

- 계약 사본의 불일치 → 원본 commit·체크섬 고정과 양쪽 호환성 검증을 구현 작업에 명시한다.
- 이전 리뷰 연결 유실 → 원본 보존, 작업 번호 유지, 이동표 및 상대 링크 검증으로 확인한다.
- 분리를 기능 구현 완료로 오해 → README와 변경 목록에 계획 단계임을 밝히고 모든 기능 작업을 미완료로 유지한다.

## Migration Plan

원본을 보존한 뒤 서버·앱 계획을 작성하고 위키를 갱신한다. 61개 작업의 목적지와 명세 시나리오 보존, 문서 형식·링크, 두 저장소 strict 검증을 확인한 후 기존 혼합 활성 계획을 제거한다. 마지막으로 이 관리 변경만 아카이브하고 재검증한다. 런타임·DB 배포는 없다.
