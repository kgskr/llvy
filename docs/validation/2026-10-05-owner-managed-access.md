# 세 역할·오너의 관리자 지정 검증 — 2026-10-05

대응하는 OpenSpec 변경은 `introduce-owner-managed-admin-access`다. 인증·DB·감사로그·
개인정보 조회 경계를 먼저 구현한 뒤, 세 서브에이전트가 오너 화면, 일반 사용자 조회 화면,
회귀 테스트와 운영 문서를 분담했다. 기존 공유 업로더·관리자 역할을 아래 세 역할로 교체했다.

## 구현 범위

| 역할        | 허용 범위                                              |
| ----------- | ------------------------------------------------------ |
| 일반 사용자 | 게임·모임원 조회. 모임원 이름 가운데 마스킹, 생년 제거 |
| 관리자      | 기존 리플레이 업로드·모임원·계정·게임 관리             |
| 서비스 오너 | 관리자 기능, 관리자 지정·취소, 감사로그 조회           |

- 하나의 비밀키 입력으로 서버가 역할을 결정한다. 조회·오너는 서로 다른 공유 키,
  관리자는 모임원별 키를 사용한다. 독립적인 `AUTH_SECRET`으로 v4 세션을 서명한다.
- 오너의 모임원 관리 표에서 정보 수정 옆 관리자 권한 열로 지정·취소한다. 지정 시 암호학적
  난수로 영어 대문자·소문자·숫자가 모두 포함된 16자 키를 발급하며, DB에는 SHA-256만 저장한다.
  원문은 성공한 최초 응답에서만 표시한다. 재조회·재발급 기능은 없고 취소 후 다시 지정한다.
- DB의 활성 발급 건은 모임원별 하나다. 취소된 발급 ID의 키·세션은 거부하며, 재지정해도
  이전 발급 ID는 살아나지 않는다. 변경 트랜잭션에서 현재 관리자 자격을 잠금으로 재확인한다.
- 일반 사용자는 게임·모임원 메뉴만 보며 업로드와 관리 직접 호출도 거부된다.
  `김민수 → 김*수`, `김수 → 김*`로 표시한다. 원래 이름과 생년은 서버 조회 모델에서 제거하여
  화면뿐 아니라 클라이언트에 전달되는 데이터에도 포함하지 않는다. 관리자·오너는 원래 정보를 본다.
- 관리자 지정·취소와 감사로그 조회는 페이지, Server Action, 서비스 조회 함수에서 오너만 허용한다.
- 로그인 성공·실패·로그아웃, 관리자 지정·취소, 모임원 등록·수정, 계정 연결·해제,
  게임 날짜 수정·복원·제외·복구, 리플레이 예약·처리 결과를 감사로그로 남긴다.
  로그인 제한에 걸린 반복 시도는 클라이언트별 60초에 한 번으로 기록량을 제한한다.
- 데이터 변경과 성공 감사기록은 같은 DB 트랜잭션으로 저장한다. 실행 당시 역할·모임원·
  발급 ID·이름, 대상, 결과, 변경 전후, 요청 ID를 보관하며 비밀키·해시·세션 쿠키는 기록하지 않는다.
- 업로드 예약은 실행자와 세션에 묶이며 Blob 토큰 발급과 처리에서도 일치 여부를 검사한다.
  파일 저장 직전에 현재 관리자 권한을 재확인한다. 만료 정리는 기존 게임 원본을 보존하고,
  최종 결과가 없는 예약의 성공·실패 감사기록과 예약 삭제를 함께 처리한다.

## 로컬 브라우저 검사

실제 Next.js 개발 서버에서 세 역할을 설명하는 로그인 화면을 확인했다.
미인증 상태로 `/upload`와 `/admin/audit`에 직접 접근하면 해당 목적지를 포함한 로그인
화면으로 이동함을 확인했다. 인증된 오너의 발급·취소와 관리자·일반 사용자의 화면 조작은
브라우저로 수행하지 않았으며 자동화된 화면·Action·DB 통합 테스트로 검증했다.

## 배포 경계와 적용 순서

이 기록은 로컬 구현·검증 결과다. 운영 DB 마이그레이션, 환경변수 변경, 앱 배포와 실제
Vercel Blob·Neon 업로드는 수행하지 않았다. PGlite 검사는 실제 다중 연결 PostgreSQL의
잠금 경합을 증명하지 않으므로 Preview에서 지정 취소와 진행 중 변경의 경합을 확인해야 한다.

1. 대상 DB를 백업하고 `npm run db:migrate`로 새 `0004_lazy_spitfire.sql`을 포함한 이력을 적용한다.
2. `READ_PASSWORD`, 새 `OWNER_PASSWORD`, 두 키와 독립적인 32바이트 이상 `AUTH_SECRET`을 설정한다.
3. 새 앱을 배포하고 재로그인·새 업로드 시작을 안내한다. 기존 v1/v2/v3 세션은 거부한다.
4. 오너가 관리자 키를 발급하고 각 모임원에게 전달한다. 기존 `ADMIN_PASSWORD`는 폐기한다.
5. [배포 후 확인 항목](../deployment.md#배포-후-확인)을 Preview DB·Blob에서 검증한다.

상세한 키 전환과 마이그레이션 순서는 [배포 안내](../deployment.md#권한-분리-업데이트와-키-교체)에 있다.
