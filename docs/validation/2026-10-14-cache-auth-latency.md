# 캐시 장애 대기와 인증 중복 조회 검증

## 구현

Redis 연결·준비·명령의 1초 제한을 각각 100ms로 줄였다. 실패 연결 제거, 5초 재시도 간격,
TLS, DB 대체, TTL과 원자적인 검색 인덱스 게시 계약은 유지한다.

페이지·레이아웃·읽기 DAL의 `getReadSession()`은 React 렌더 안에서 인증 Promise를 공유한다.
자동완성 GET은 AsyncLocalStorage 요청 범위를 만들어 핸들러와 DAL의 인증을 한 번으로 합친다.
`getSession()`·변경 guard·업로드 직전 재검증과 transaction 권한 잠금은 최신 상태를 확인한다.

## 로컬 증거

Node.js 24.21.0에서 실제 Redis 7·PostgreSQL 17·리플레이 파일을 지정한 `npm run check`가
45개 파일, 792개 테스트를 건너뛰지 않고 통과했다. lint·typecheck·build·format도 통과했다.
Redis 전용 검사 49개와 OpenSpec strict의 변경 12개가 통과했다.

- 응답을 차단하는 로컬 TCP 프록시로 실제 Redis 준비·명령 실패를 재현했다. DB loader는 한 번
  실행되고 종전 1초 제한보다 빠르게 대체되었다. 가짜 시계 테스트로 100ms 준비 제한도 확인했다.
- 실제 자동완성 핸들러와 검색 DAL의 인증 join은 요청당 1회였다. 세션 폐기 후 다음 요청은
  DB를 다시 확인하고 401을 반환했다. 정상·빈 입력·잘못된 쿼리 형식을 포함했다.
- 동시 요청의 쿠키 분리, 진행 중 Promise 공유, null·오류 공유와 다음 요청 재시도,
  읽기 후 권한이 사라졌을 때 fresh guard가 거부하는 회귀가 통과했다.
- React 점검에서는 렌더 전용 `cache()` 사용, 요청 간 인증 상태 공유 방지, 서버 인가 유지와
  클라이언트로 인증 객체를 전달하지 않는 것을 확인했다. RSC 메모이제이션은 React의 요청 범위에
  의존하며 일반 함수 호출 테스트를 실제 React 렌더링 증거로 취급하지 않는다.

## 운영 확인 범위

애플리케이션 커밋 `f8acb07`이 운영 도메인의 싱가포르 배포에서 READY에 도달한 것을 확인했다.
인증된 검색 API와 모임원 목록의 첫·반복 조회는 200, 로그인 페이지는 200, 비로그인 검색 API는
401이었다. 100ms 제한에서도 Upstash의 자동완성 인덱스와 viewer 목록 캐시가 생성되었고,
검증 구간의 새 배포 로그에서 캐시 연결 실패 경고는 조회되지 않았다.

전체 응답 시간에는 초기 실행·인증 DB·캐시 재구축·브라우저 네트워크 지연도 남아 있다.
100ms 캐시 실패 제한을 전체 요청이 100ms 안에 끝난다는 뜻으로 해석하지 않는다.
운영 서비스에 강제로 Redis 장애를 주입하거나 계정 권한·업로드·외부 Discord·Cron 동작을
변경하는 검증은 포함하지 않았다. 인증 조회 횟수와 장애 제한은 위 로컬 재현으로 검증했다.
