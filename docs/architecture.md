## 계정 연결과 모임원 전적

계정은 PUUID를 우선 사용하고, 없는 리플레이는 Riot ID의 이름·태그로 식별합니다.
처음 보는 계정은 모임원에 연결하지 않은 상태로 저장됩니다.
미연결 목록에는 활성 경기에서 발견한 계정만 표시하고 게임 수도 활성 경기만 집계합니다.
제외 경기에만 남은 계정과 경기 기록이 없는 계정은 표시하지 않으며, 경기 복구 시 다시 표시됩니다.
관리 화면의 모임원·미연결 계정 표는 각각 10개씩 독립적으로 페이징합니다. 모임원 ID를 먼저
페이징한 뒤 계정을 연결하므로 한 모임원의 계정 수에 따라 페이지 인원이 줄지 않습니다.
계정 연결 선택 목록은 표의 현재 페이지와 관계없이 모든 모임원을 포함합니다.

같은 Riot ID의 기존 계정이 하나뿐이고 모임원에 연결되지 않았을 때만 PUUID를 추가합니다.
이미 연결된 계정은 업로드된 PUUID로 변경하지 않습니다. 새 PUUID 계정은 미연결로
남으므로 관리 화면에서 검토해 연결해야 합니다. 여러 신원이 같은 이름을 쓰는 경우도
자동 병합하지 않습니다.

모임원 전적은 현재 연결된 모든 계정의 활성 경기를 합산합니다. 계정 연결·해제는
과거 전적에도 즉시 반영되며, 페이지는 25건 단위이고 전체 통계는 페이지와 무관합니다.
승률은 승패가 확인된 경기만, 평균은 해당 값이 있는 경기만 계산합니다.
한 경기에 같은 모임원의 계정이 여러 개 연결되면 경기 수는 한 번만 세고 승패·평균에서는
제외합니다. 화면의 중복 연결 안내를 보고 연결을 바로잡으면 다시 집계됩니다.

모임원 삭제는 관리자·오너가 실제 `DELETE`로 처리합니다. 모임원 행 잠금 후 활성 관리자
발급 건이 없음을 확인하므로 관리자는 먼저 오너가 권한을 취소해야 합니다. 삭제 트랜잭션은
연결 계정의 `member_id`·`linked_at`을 비우고 취소된 자격증명과 모임원을 삭제합니다.
계정·참가자·경기·과거 감사로그는 보존하며 연결 해제와 삭제 감사기록도 같은 트랜잭션에 저장합니다.
계정 연결도 대상 모임원을 먼저 잠가 삭제와 계정 변경의 잠금 순서를 맞춥니다.

## 경기 날짜·코멘트와 제외

원본 날짜는 파일의 `lastModified`에서 한국 날짜를 추출하고, 없으면 업로드한 한국 날짜를 사용합니다.
출처는 `games.played_at_source`에 기록합니다. 직접 수정한 날짜는
`games.played_at_override`에 별도로 저장하므로 원본 날짜로 되돌릴 수 있습니다.
두 날짜 열은 PostgreSQL `date`이며 앱에는 `YYYY-MM-DD` 문자열로 전달합니다.
관리 입력은 날짜만 받으며 2009년 1월 1일부터 한국 날짜 기준 내일까지 허용합니다.
기존 시각은 `AT TIME ZONE 'Asia/Seoul'`로 변환 후 날짜만 남깁니다. 업로드·제외·감사 시각과
경기 진행 시간은 운영 이력과 통계에 사용하므로 그대로 유지합니다.

경기당 코멘트 하나를 `games.comment`에 저장합니다. 관리자·오너가 추가·수정·비우고,
일반 사용자는 읽을 수 있습니다. 공백을 포함한 Unicode 코드 포인트 30개까지 허용하며
문자열을 자르거나 공백을 제거하지 않습니다. 빈 문자열은 `NULL`로 처리합니다.
서버 검증과 DB `char_length` 제약을 함께 사용하며 변경 전후와 감사로그를 원자적으로 저장합니다.

제외한 경기는 `games.excluded_at`으로 표시하며 기본 목록과 모임원 집계에서 빠집니다.
경기·참가자·Blob은 보존되고 복구할 수 있습니다. 같은 파일을 다시 올려도 중복 생성하거나
자동 복구하지 않습니다.

## 업로드와 원본 보존

1. 브라우저가 `POST /api/uploads`로 업로드를 시작합니다. 서버는 업로드 ID, nonce,
   예약 경로 `replays/<uploadId>.rofl`과 Blob 접근 모드를 발급하고 nonce는 해시로 저장합니다.
   관리자·오너만 시작할 수 있으며 예약에 실행자 역할·모임원·발급 ID를 저장합니다.
2. `/api/blob/upload`는 유효한 바인딩에만 정확히 그 경로의 업로드 토큰을 발급합니다.
   덮어쓰기와 랜덤 접미사는 허용하지 않습니다. 브라우저가 Blob으로 직접 업로드하므로
   원본 파일을 앱 함수의 요청 본문에 넣지 않습니다. read-write 토큰은 서버에만 남습니다.
3. `/api/process`는 nonce·상태·만료, 현재 토큰의 스토어와 접근 모드, 예약 경로를
   검증한 뒤 원본을 가져옵니다. 예약을 시작한 관리자 발급 건 또는 오너만 처리할 수 있습니다. URL의 query·fragment는 제거하며 다른 스토어·경로와
   다운로드 리디렉션은 거부합니다. private 파일은 검증된 URL에 서버 토큰으로 접근합니다.
4. 실제 파일을 파싱해 현재 권한을 다시 확인하고 하나의 트랜잭션으로 저장합니다.
   저장과 성공 감사로그는 원자적으로 기록하고 업로드 ID로 성공·중복·실패 사건을 연결합니다. 중복·파싱 실패 시에는 해당
   바인딩에 묶인 새 Blob만 삭제하고 기존 경기의 원본은 보존합니다.
5. 바인딩은 한 번 처리하면 소비되며 발급 후 30분에 만료됩니다. 성공 후 상태 기록은
   한 번 재시도합니다. 기록 실패나 DB 커밋 결과가 불확실한 오류에서는 원본을 보존합니다.
6. 만료 바인딩과 사용하지 않는 원본은 [정리 작업](deployment.md#만료-업로드-정리)이
   처리합니다. 게임이 참조하는 원본은 삭제하지 않습니다.

관련 구현은 [`pending-upload.ts`](../src/lib/pending-upload.ts),
[`pending-upload-store.ts`](../src/lib/pending-upload-store.ts),
[`blob-store.ts`](../src/lib/blob-store.ts),
[`expired-upload-cleanup.ts`](../src/lib/expired-upload-cleanup.ts)에 있습니다.

## 조회 캐시와 닉네임 검색

조회 모델은 세션 확인 후 [Valkey](valkey.md)에 역할별로 투영한 JSON 결과를 60초간 캐시합니다.
`VALKEY_URL`의 TLS 연결은 서버 인스턴스에서 재사용하며 캐시 장애·미설정 시 DB를 직접 조회합니다.
데이터 변경이 커밋된 뒤 공유 세대 UUID를 교체하고, 이전 세대로 시작한 조회는 이전 키에만 저장합니다.
관리자 자격증명과 감사로그·요청 제한은 캐시하지 않습니다.

일반 사용자 랜딩의 입력은 로그인한 사용자용 `/api/search/autocomplete`에 연결됩니다.
[`nickname-autocomplete.ts`](../src/lib/nickname-autocomplete.ts)는 모임원에 연결되고 활성 경기 기록이
있는 계정의 닉네임·태그만 공유 Sorted Set으로 인덱싱합니다. 모든 score를 0으로 두고 정규화한
UTF-8 접두어 범위를 `ZRANGE ... BYLEX`로 조회해 최대 10개를 반환합니다. 별도 Hash에 원래 표시값을
보관하고 실명·생년은 인덱스에 넣지 않습니다. Lua로 완료 표식·Sorted Set·Hash를 함께 확인하고
임시 인덱스를 게시합니다. 인덱스는 동일 캐시 세대와 60초 TTL을 사용하며 처음 필요한 요청에서
재구축합니다. 같은 인스턴스의 중복 재구축은 하나의 Promise로 합칩니다.

`/search` 제출은 [`nickname-search.ts`](../src/lib/nickname-search.ts)의 `resolveNicknameMember()`로
닉네임과 선택적 태그를 정확히 일치시키고 현재 DB 계정 연결·활성 경기 기록을 다시 확인합니다.
단일 모임원은 전적으로 이동하고 여러 모임원이면 최대 20개 선택지, 없으면 `/search/not-found` 안내를
표시합니다. 일반 사용자 선택지 이름은 마스킹합니다. 내부 부분 문자열 검색 함수의 캐시 결과는
제출의 연결 판단에 사용하지 않습니다. 검색 읽기는 감사로그 대상이 아닙니다.

입력은 NFC·대소문자·양끝 공백을 정규화하고 자동완성은 닉네임 및 `닉네임#태그접두어`를
지원합니다. 인덱스·정확한 제출·부분 검색은 공통 JavaScript 정규화 함수를 사용합니다.
정확한 제출과 내부 부분 검색은 현재 연결·활성 계정 집합을 DB에서 읽어 JavaScript로 비교합니다.
DB collation과 JavaScript 소문자 변환이 다른 Unicode 이름도 같은 규칙으로 판단하기 위한 선택입니다.
계정 수가 커지면 DB에서 정규화된 검색 컬럼을 조회하는 방식을 검토해야 합니다.
초성·유사어·오타 보정은 지원하지 않습니다. 무효화 실패나 DB 직접 변경 때 추천이
잠시 오래될 수 있지만 제출은 현재 DB 연결을 사용합니다. TTL은 게시 후 60초이며 재구축 시간까지
포함한 변경 시점 기준의 엄격한 상한은 아닙니다. 장애·운영 검증은 [Valkey 안내](valkey.md)를 따릅니다.

## 인증과 요청 제한

`READ_PASSWORD`는 일반 조회자(viewer), `OWNER_PASSWORD`는 서비스 오너(owner)입니다.
관리자(admin)는 오너가 모임원별로 발급한 16자 난수 키로 로그인합니다. 같은 입력란의 키로
서버가 역할을 판별하고 클라이언트가 제출한 역할은 사용하지 않습니다. 관리자·오너는 업로드와
모임원·경기 관리를 수행하며, 관리자 지정·취소와 감사로그 조회는 오너만 수행합니다.
일반 사용자가 관리·업로드 페이지에 접근하면 조회 화면으로 이동하고 직접 변경 요청도 거부합니다.
일반 사용자의 기본 로그인 목적지와 LLVY 로고 링크는 `/`의 닉네임 검색 랜딩입니다.
입력 중에는 접두어 자동완성을 조회하고 검색을 제출하면 현재 연결된 모임원 전적으로 이동합니다.
게임·모임원 메뉴에서 기존 조회 화면도 이용할 수 있습니다. 관리자·오너의 기본 목적지는 `/games`입니다.

세션은 `v4.<role>.<issuedAtMs>.<uuidNonce>.<memberId-or-dash>.<credentialId-or-dash>.<base64urlHmac>`
형식의 서명된 30일 쿠키입니다. 관리자에만 모임원·발급 UUID가 들어가며 키 원문·해시는
포함하지 않습니다. 변조·만료·비정규 서명 표현과 기존 v1/v2/v3 세션은 거부합니다.
서명에는 필수 서버 전용 `AUTH_SECRET`을 사용합니다. 두 공유 키는 서로 달라야 하고
`AUTH_SECRET`은 두 키와 다른 값이며 앞뒤 공백 제거 후 UTF-8 기준 32바이트 이상입니다.
잘못된 설정은 로그인과 세션 검증을 거부합니다.

HKDF salt에 역할과 공유 역할의 현재 키를 포함합니다. `READ_PASSWORD` 교체는 일반 사용자
세션, `OWNER_PASSWORD` 교체는 오너 세션, `AUTH_SECRET` 교체는 모든 세션을 무효화합니다.
Proxy는 서명과 역할을 검사하고, 서버의 세션 조회는 관리자 발급 건이 현재 활성인지 DB에서
확인합니다. 관리자 세션에는 키 원문 없이 발급 ID를 서명합니다. 취소 후 새 발급 ID를 만들므로
재지정해도 이전 세션은 살아나지 않습니다.

[`admin-credentials.ts`](../src/lib/admin-credentials.ts)는 암호학적 난수로 대문자·소문자·숫자가
모두 포함된 16자 키를 생성하고 SHA-256만 저장합니다. 원문은 최초 발급 응답에서만 반환합니다.
모임원 행 잠금과 활성 발급 건 고유 제약으로 중복 발급을 차단합니다. 변경 트랜잭션에서는
활성 관리자 자격증명에 공유 행 잠금을 잡아 취소와 직렬화하며, 감사로그 삽입 실패 시 변경도 롤백합니다.
앱에는 로그 수정·삭제 API가 없으나 DB 운영자까지 막는 외부 불변 저장소는 사용하지 않습니다.

일반 사용자의 데이터는 [`read-model.ts`](../src/lib/read-model.ts)와
[`member-privacy.ts`](../src/lib/member-privacy.ts)에서 렌더링 전에 이름을 마스킹하고 생년 속성을
제거합니다. 한 글자는 `*`, 두 글자는 첫 글자와 `*`, 세 글자 이상은 첫·끝 글자와 가운데 `*`를
표시합니다. 현재는 성과 이름을 따로 저장하지 않아 복성을 구분하지 않습니다. 보호 데이터는
현재 세션으로 읽고 서로 다른 역할의 응답은 캐시 키를 공유하지 않습니다.

로그인은 모든 역할이 키 검증 전에 Vercel에서 확인한 IP별로 분당 10회까지 허용됩니다.
일반 `x-forwarded-for` 값은 사용하지 않으며 신뢰할 수 있는 IP를 확인하지 못하면 거부합니다.
로그인 성공·잘못된 키·로그아웃을 기록하고, 제한 초과 사건은 로그 폭증을 막도록 클라이언트별
1분에 한 번만 기록합니다. 신뢰할 수 있는 IP가 없는 요청은 공통 제한 초과 사건으로 묶습니다.
업로드 예약은 세션별 24시간에 10개, 전체 50개까지이며 Postgres 원자적 카운터로
여러 서버 인스턴스에 함께 적용합니다. 파일 처리 성공 수가 아닌 업로드 시작 횟수에 적용되며
초과 시 429를 반환합니다. 정리 엔드포인트는 별도의 `CRON_SECRET`으로 인증합니다.

## 파싱·저장 한도

| 항목                  | 한도   |
| --------------------- | ------ |
| 원본 파일             | 64MiB  |
| 참가자 수             | 10명   |
| 메타데이터            | 4MiB   |
| `statsJson`           | 256KiB |
| 참가자 객체           | 32KiB  |
| 참가자 객체 중첩 깊이 | 4      |

파싱 예산은 파서와 수집 트랜잭션 시작 전에 확인합니다. 초과한 메타데이터나 잘못된
참가자 필드 타입은 422로 거부하며, DB에 저장할 `raw_stats`·`raw_metadata`는 허용된
스칼라 필드로 축소합니다.

동시 수집의 계정 갱신 순서는 신원 기준으로 고정합니다. 교착 상태·직렬화 실패
(`40P01`·`40001`)로 롤백한 트랜잭션만 최대 3회 실행합니다. 커밋 여부가 불확실한
연결 오류는 자동 재시도하지 않습니다.

경기 상세의 DataDragon 챔피언 이름 조회는 응답 본문까지 2초로 제한합니다.
조회 실패나 시간 초과 시 리플레이의 내부 이름을 표시합니다.
