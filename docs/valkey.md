# Layerbase Valkey

[문서 목록](README.md) · [배포·운영](deployment.md)

## Vercel 연결

Layerbase에서 **Valkey 9** DB를 만들고 Vercel 프로젝트와 연결합니다. 연결 정보의 TLS 주소가
서버 환경변수 `VALKEY_URL`에 들어가도록 설정합니다. 포트는 6379이며 앱은 이 값으로
`ioredis` 연결 하나를 서버 인스턴스 안에서 재사용합니다.
[Layerbase 연결 안내](https://layerbase.com/docs/cloud/connecting/valkey)를 참고하세요.

```dotenv
VALKEY_URL="rediss://default:<password>@<host-from-layerbase>:6379"
VALKEY_KEY_PREFIX="llvy"
```

REST URL이나 API 토큰은 필요하지 않습니다. `NEXT_PUBLIC_` 변수로 만들지 마세요.
Vercel의 Production·Preview·Development에 연결되는 DB와 환경변수 범위를 확인한 뒤
재배포합니다. 로컬은 해당 환경의 URL을 `.env.local`에 넣습니다. 키나 URL 원문을
문서·로그·Git에 남기지 마세요. 운영은 TLS 인증서 검증과 호스트 SNI를 사용합니다.

## 조회 캐시와 닉네임 검색

- 게임 목록·상세, 모임원 목록·전적의 조회 결과를 60초간 저장합니다.
- 매번 현재 세션을 검증한 후 캐시에 접근합니다. 역할별 키를 사용하고 일반 사용자용
  이름을 마스킹하고 생년을 제거한 결과만 저장합니다.
- 인증·현재 관리자 자격증명·관리자 지정 목록·감사로그·요청 제한은 PostgreSQL에서 확인합니다.
- 게임 수정·제외·복구, 모임원 변경·삭제, 계정 연결·해제, 관리자 지정·취소와 신규 리플레이
  저장이 커밋되면 캐시 세대를 교체합니다. 같은 리플레이의 중복 처리는 데이터 캐시를 교체하지 않습니다.

일반 사용자의 첫 화면에서 라이엇 닉네임을 입력하면
`GET /api/search/autocomplete?nickname=...`로 최대 10개 후보를 조회합니다. 로그인한 사용자만 사용할 수 있고,
**모임원에 연결되어 있으며 활성 경기 기록이 있는 계정**만 대상으로 합니다.
원래 이름·태그를 표시하지만 모임원 실명·생년은 자동완성 응답에 포함하지 않습니다.

후보는 닉네임 접두어로 찾습니다. NFC·대소문자·양끝 공백을 정규화하며 `닉네임#태그접두어`도
지원합니다. 한국어 초성·오타 보정·유사어 검색은 지원하지 않습니다. 실제 검색은 Riot API를
호출하지 않고 이 서비스에 저장한 계정과 전적만 사용합니다.

검색 버튼이나 Enter로 `/search?nickname=...`에 제출하면 닉네임 전체를 일치시키고, `#태그`를 입력했다면
태그도 전체를 일치시킵니다. 현재 계정 연결을 **매번 PostgreSQL에서 확인**합니다.
한 모임원으로 확정되면 해당 모임원 전적으로 이동하고, 태그 없이 같은 닉네임이 여러 모임원에
연결되어 있으면 최대 20개 선택지를 표시합니다. 같은 모임원의 여러 계정만 일치하면 바로 이동합니다.
현재 일치하는 계정이 없거나 연결 해제·삭제·경기 제외로 조회 대상에서 빠졌다면
`/search/not-found`에서 없는 사용자로 안내합니다.
선택지의 모임원 이름도 일반 사용자에게는 마스킹합니다. 검색 읽기 요청은 감사로그에 추가하지 않습니다.

자동완성 API는 `{ suggestions: [{ id, gameName, tagLine }] }` 형식으로 응답하며 HTTP 응답은
`Cache-Control: private, no-store`입니다. Valkey 인덱스 재사용과 브라우저 응답 저장은 별개입니다.
미인증 요청은 401로 거부하고 DB 등 조회 오류는 내부 상세를 포함하지 않는 오류로 응답합니다.

## 자동완성 인덱스

[`nickname-autocomplete.ts`](../src/lib/nickname-autocomplete.ts)는 공유 캐시 세대별로
Sorted Set·표시용 Hash·완료 표식을 함께 사용합니다. Sorted Set에는 정규화한
`닉네임#태그`와 계정 ID를 넣고 모든 score를 0으로 지정합니다. 표시용 Hash에는 계정 ID·닉네임·태그만
저장하며 모임원 실명·생년은 저장하지 않습니다.

접두어를 UTF-8 바이트 범위로 바꾸고 `ZRANGE ... BYLEX LIMIT 0 10`으로 조회합니다.
한글과 이모지도 같은 범위 규칙을 사용합니다. 동일 score와 바이트 비교 조건은
[Valkey ZRANGE 문서](https://valkey.io/commands/zrange/)를 따릅니다.

인덱스는 앱 시작이나 배포 때 미리 만들지 않습니다. 첫 유효한 자동완성 요청에서 인덱스가
없으면 DB의 대상 계정을 읽어 생성합니다. 같은 서버 인스턴스에서 동시에 시작한 동일 세대의
재구축은 하나의 Promise를 공유합니다. 여러 서버 인스턴스 사이에는 분산 구축 잠금을 두지 않습니다.

임시 키에 구성한 뒤 Lua로 완료 인덱스를 게시하고 TTL 60초를 설정합니다. 조회도 Lua에서
완료 표식·Sorted Set·Hash를 함께 확인하여 일부 키만 남은 상태나 손상된 데이터를 miss로 처리합니다.
이 게시·조회는 [Valkey의 원자적 스크립트 실행](https://valkey.io/topics/programmability/)을 사용합니다.
TTL 만료·부분 키 제거·새 캐시 세대에서는 다음 요청이 다시 구성합니다. 게시 오류가 생겨도 해당
요청은 이미 읽은 DB 결과로 후보를 반환합니다. 연결이 없거나 장애가 나면 DB 조회로 접두어 후보를 만듭니다.

부분 문자열 검색용 `searchStoredNicknames()`도 서버 함수로 유지합니다. 같은 JavaScript NFC·trim·
소문자 정규화 함수를 인덱스·정확한 검색·부분 검색에 사용해 PostgreSQL collation의 대소문자
처리 차이를 피합니다. 부분 검색은 문자열의 문자 그대로 포함 여부를 검사하므로 `%`·`_`·역슬래시를
와일드카드로 취급하지 않습니다. 선택한 태그는 정확한 일치이며 최대 20개 결과를 캐시합니다.
정확한 제출과 부분 검색은 현재의 활성·연결 계정 집합을 DB에서 읽은 뒤 JavaScript로 걸러냅니다.
현재 소규모 모임의 정규화 일관성을 위한 선택이며, 계정 수가 크게 늘면 정규화 검색 컬럼 등으로
DB 조회 비용을 줄이는 설계를 검토해야 합니다. 첫 화면의 전적 이동은 부분 검색 캐시가 아닌
`resolveNicknameMember()`의 현재 연결 확인을 사용합니다.

키 공간은 `VALKEY_KEY_PREFIX`, 배포 환경, PostgreSQL 호스트·DB 이름의 해시와 스키마 버전으로
분리됩니다. 같은 DB를 쓰는 독립 프로젝트는 서로 다른 `VALKEY_KEY_PREFIX`를 사용하세요.
같은 프로젝트의 서버 인스턴스는 동일한 prefix를 써야 무효화가 공유됩니다.

## 장애 동작

URL이 없으면 캐시 없이 동작합니다. 연결·명령 대기는 각각 1초로 제한하고 오프라인 명령
큐와 자동 재전송을 사용하지 않습니다. 연결 실패 후 5초간 직접 DB를 사용한 뒤 다시 시도합니다.
경고는 30초마다 최대 한 번 기록하며 URL·비밀번호·원본 오류는 출력하지 않습니다.

조회 실패나 손상된 JSON은 캐시 miss로 처리합니다. 256 KiB를 넘는 결과는 저장하지 않습니다.
캐시 무효화 실패가 이미 완료한 DB 변경을 실패로 돌리지 않습니다. 게시한 캐시 항목의 TTL은
60초이므로 실패한 무효화나 앱 밖의 DB 변경 후 잠시 이전 값·추천이 보일 수 있습니다.
DB와 캐시를 원자적으로 갱신하는 구조는 아닙니다. TTL은 항목 게시 시점부터 계산하므로 느린
조회·재구축이 변경과 겹치면 그 처리 시간까지 포함한 엄격한 ‘변경 후 60초’ 보장은 아닙니다.
자동완성 후보가 잠시 남아 있어도 검색 제출 시 현재 DB 연결과 활성 경기 기록을 다시 확인하므로
연결 해제·삭제된 계정의 오래된 후보만으로 이전 모임원 전적에 이동하지 않습니다.

## Podman 테스트

운영 연결 주소를 테스트 변수에 넣지 않습니다. 테스트는 로컬 루프백 컨테이너만 허용하고,
PostgreSQL 데이터는 실제 마이그레이션을 적용한 메모리 PGlite를 사용합니다.

```bash
podman machine start  # 이미 실행 중이면 생략
podman run --detach --name llvy-valkey-test \
  --publish 127.0.0.1:16379:6379 docker.io/valkey/valkey:9 \
  valkey-server --save '' --appendonly no
podman exec llvy-valkey-test valkey-cli INFO server

LLVY_VALKEY_TEST_URL="redis://127.0.0.1:16379" npm run test:valkey
# Valkey 통합 검증을 전체 품질 검사에 포함:
VALKEY_URL="" LLVY_VALKEY_TEST_URL="redis://127.0.0.1:16379" npm run check

podman rm --force llvy-valkey-test
```

이미지의 실제 `valkey_version`이 9 계열인지 확인합니다. `test:valkey`는 테스트 URL이 없으면
설정 오류로 종료하고, 일반 `npm test`에서는 지정하지 않은 컨테이너 통합 테스트를 건너뜁니다.
테스트마다 UUID 키 공간을 사용하고 해당 키만 제거합니다. `FLUSHDB`나 `FLUSHALL`은 사용하지 않습니다.

## 배포 후 확인

1. 같은 조회를 두 번 수행해 역할별 캐시 키와 TTL을 확인합니다. 다른 서버 인스턴스에서도
   동일한 세대와 결과를 사용하며 변경 후 새 세대로 조회하는지 확인합니다.
2. 일반 사용자 첫 화면에서 한글·영문·이모지 닉네임을 입력하고 최대 10개 접두어 후보를
   확인합니다. NFC·대소문자·`#태그접두어`·키보드 선택·검색 제출을 확인합니다.
3. 정확한 닉네임·태그로 단일 모임원 전적에 이동하고, 태그 없는 동명 계정은 모임원 선택으로,
   없는 닉네임·미연결 계정·제외 경기만 있는 계정은 없는 사용자 안내로 이어지는지 확인합니다.
4. 오너로 조회한 뒤 일반 사용자로 조회해 원문 모임원 이름·생년이 일반 사용자 응답과 캐시에
   없는지 확인합니다. 자동완성에는 계정 ID·닉네임·태그만 있고, 선택 화면 이름은 마스킹되어야 합니다.
5. 자동완성을 먼저 조회한 다음 계정 연결·해제·모임원 삭제·경기 제외·복구를 수행합니다.
   다음 추천이 갱신되고, 이전 후보를 제출해도 현재 연결을 기준으로 처리하는지 확인합니다.
6. 첫 요청·TTL 만료·인덱스 일부 키 제거에서 재구축하고 잘못된 부분 인덱스를 반환하지 않는지
   확인합니다. 재구축이 겹친 요청과 여러 서버 인스턴스의 응답도 확인합니다.
7. 관리자 지정 취소 후 캐시가 있어도 이전 세션의 페이지·자동완성 API 접근이 거부되는지 확인합니다.
8. 별도 Preview에서 연결 실패 시 조회·검색과 데이터 변경이 계속 가능한지 확인합니다.
   무효화 실패 시 남은 TTL 동안 추천이 오래될 수 있음을 확인하고, 제출은 현재 DB 연결을 사용해야 합니다.
9. 검색 읽기만으로 감사로그가 증가하지 않고 로그인·데이터 변경 기록은 유지되는지 확인합니다.

Podman 검증은 명령·캐시와 로컬 데이터 동작의 증거입니다. 실제 Layerbase TLS·Vercel 연결 수·
휴면 복귀·네트워크 지연은 이 배포 확인으로 구분합니다. 캐시를 끄려면 URL을 제거하고 재배포합니다.
