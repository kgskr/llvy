# Upstash Redis

[문서 목록](README.md) · [배포·운영](deployment.md)

## Vercel 연결

Vercel Storage에서 **Upstash for Redis**의 Free 데이터베이스를 만들고 Primary Region을
**Singapore (`ap-southeast-1`)**로 선택합니다. 앱 함수도 `vercel.json`의 `sin1`에서 실행합니다.
운영 프로젝트의 Production 환경에만 연결하고, 주입된 TCP/TLS 주소 `REDIS_URL`을 사용합니다.

```dotenv
REDIS_URL="rediss://default:<password>@<host-from-upstash>:6379"
REDIS_KEY_PREFIX="llvy"
```

`ioredis`는 Redis 클라이언트이며 Upstash의 TCP/TLS 연결을 지원하므로 그대로 사용합니다.
REST URL·토큰은 이 코드 경로에 필요하지 않습니다. `NEXT_PUBLIC_` 변수로 만들지 마세요.
앱은 서버 인스턴스마다 연결 하나를 공유하고 인증서 검증과 호스트 SNI를 사용합니다.
[Upstash 연결 안내](https://upstash.com/docs/redis/troubleshooting/econn_reset)를 참고하세요.

변경 전 `VALKEY_URL`과 `VALKEY_KEY_PREFIX`는 더 이상 읽지 않습니다. Upstash 연결의
`REDIS_URL`을 저장한 뒤 재배포하세요. 설정이 없으면 캐시 없이 PostgreSQL로 조회합니다.
기존 Layerbase 데이터는 복사하지 않으며 새 캐시는 첫 요청부터 채워집니다.
Preview와 로컬에는 별도 개발용 Redis를 사용합니다. 운영 비밀번호를 로컬 테스트로 가져오거나
URL 원문을 문서·로그·Git에 남기지 마세요.

## 조회 캐시와 이름·닉네임 검색

- 게임 목록·상세, 모임원 목록·전적의 조회 결과를 60초간 저장합니다.
- 매번 현재 세션을 검증한 후 캐시에 접근합니다. 역할별 키를 사용하고 일반 사용자용
  결과는 이름 원문을 유지하고 생년을 제거한 뒤 저장합니다. namespace v2로 이전 마스킹 결과와 분리합니다.
- 인증·현재 관리자 자격증명·관리자 지정 목록·감사로그·요청 제한은 PostgreSQL에서 확인합니다.
- 게임 수정·제외·복구, 모임원 변경·삭제, 계정 연결·해제, 관리자 지정·취소와 신규 리플레이
  저장이 커밋되면 캐시 세대를 교체합니다. 같은 리플레이의 중복 처리는 데이터 캐시를 교체하지 않습니다.

메인 폼은 `GET /api/search/autocomplete?q=...`로 모임원 이름과 Riot ID를 함께 추천합니다.
이름은 계정·전적 여부와 관계없이 등록 모임원 전체를 대상으로 하고, Riot ID는 **모임원에 연결되고
활성 경기 기록이 있는 계정**만 대상으로 합니다. NFC·trim·소문자 정규화 후 접두어를 찾으며
Riot ID의 `닉네임#태그접두어`도 지원합니다. 이름의 `#`·`%`·`_`는 일반 문자입니다.
초성·오타 보정·유사어 검색과 외부 Riot API 호출은 하지 않습니다.

`q` 응답은 `{ suggestions: [...] }`이며 후보는 두 종류입니다.

- `{ kind: "member", id, name, accounts: [{ gameName, tagLine }] }`: 연결 계정 미리보기 최대 2개.
- `{ kind: "riot-account", id, gameName, tagLine }`: 기존 Riot ID 후보.

종류별 우선 5개를 배정하고 남는 자리를 다른 종류에 할당해 합계 10개를 반환합니다.
모임원 후보가 먼저이며 종류 안에서는 정규화한 이름/Riot ID의 UTF-8 바이트·UUID 순서입니다.
생년·Discord 계정 정보·자격증명은 인덱스와 응답에 넣지 않습니다. 클라이언트도 종류·UUID·미리보기
배열을 검증하고 허용 필드만 투영합니다. 이름은 모든 로그인 역할에게 원문으로 표시합니다.

직접 `GET /search?q=...`로 제출하면 이름 전체 또는 Riot ID의 정확 일치 결과를 현재 PostgreSQL에서
구합니다. 같은 모임원의 여러 계정은 한 명으로 합친 뒤 판정하며, 한 명은 전적, 여러 명은 20명씩
페이지가 있는 선택 목록, 없으면 `/search/not-found`입니다. 이름과 다른 모임원의 닉네임이 겹쳐도
한쪽을 우선하지 않습니다. 페이지 링크는 검색어와 입력 모드를 유지합니다.
이름 후보는 `/members/{id}`로 이동하며 상세에서 현재 이름·존재와 세션을 다시 확인합니다.
Riot 후보는 `/search?nickname=...`로 이동해 현재 계정 연결과 활성 경기를 확인합니다.

기존 `nickname` 전용 요청은 이름을 검색하지 않습니다. 자동완성 응답도 기존
`{ suggestions: [{ id, gameName, tagLine }] }` 형태를 유지합니다. 직접 제출은 모임원별 그룹화와
페이지 처리를 공유합니다. API 응답은 `Cache-Control: private, no-store`이며, 미인증은 401,
반복 파라미터나 `q`/`nickname` 혼합은 400, DB 조회 실패는 상세를 숨긴 503입니다.
빈 입력·100 code point 초과·제어 문자·잘못된 UTF-16은 빈 후보 또는 없는 사용자로 처리합니다.
검색 읽기는 감사로그에 추가하지 않습니다.

## 자동완성 인덱스

[`autocomplete-index.ts`](../src/lib/autocomplete-index.ts)는 공유 캐시 세대 아래 두 인덱스를 관리합니다.
Riot 인덱스 `autocomplete:v1`은 정규화한 `닉네임#태그 + 구분자 + 계정 UUID`와 기존 표시값을,
이름 인덱스 `member-autocomplete:v1`은 `이름 + 구분자 + 모임원 UUID`와 최소 모임원 후보를 저장합니다.
각 인덱스는 `:names` Sorted Set, `:accounts` 표시 Hash, `:ready` 완료 표식으로 구성합니다.
모든 score는 0이고 이름과 계정 미리보기는 단일 join 조회로 구성해 N+1을 피합니다.

접두어를 UTF-8 바이트 범위로 바꾸고 `ZRANGE ... BYLEX LIMIT 0 10`으로 조회합니다.
한글과 이모지도 같은 범위 규칙을 사용합니다. 동일 score와 바이트 비교 조건은
[Redis ZRANGE 문서](https://redis.io/docs/latest/commands/zrange/)를 따릅니다.

인덱스는 앱 시작이나 배포 때 미리 만들지 않습니다. 첫 유효한 자동완성 요청에서 인덱스가
없으면 DB의 대상 모임원 또는 계정을 읽어 생성합니다. 같은 서버 인스턴스에서 동시에 시작한 동일 세대의
재구축은 하나의 Promise를 공유합니다. 여러 서버 인스턴스 사이에는 분산 구축 잠금을 두지 않습니다.

임시 키에 구성한 뒤 Lua로 완료 인덱스를 게시하고 TTL 60초를 설정합니다. 조회도 Lua에서
완료 표식·Sorted Set·Hash를 함께 확인하여 일부 키만 남은 상태나 손상된 데이터를 miss로 처리합니다.
이 게시·조회는 [Redis의 원자적 스크립트 실행](https://redis.io/docs/latest/develop/programmability/)을 사용합니다.
TTL 만료·부분 키 제거·새 캐시 세대에서는 다음 요청이 다시 구성합니다. 게시 오류가 생겨도 해당
요청은 이미 읽은 DB 결과로 후보를 반환합니다. 연결이 없거나 장애가 나면 같은 정렬·할당 규칙으로 DB 결과를 사용합니다. 두 DB 소스 중 하나라도 실패하면 부분 목록을 반환하지 않습니다.

부분 문자열 검색용 `searchStoredNicknames()`도 서버 함수로 유지합니다. 같은 JavaScript NFC·trim·
소문자 정규화 함수를 인덱스·정확한 검색·부분 검색에 사용해 PostgreSQL collation의 대소문자
처리 차이를 피합니다. 부분 검색은 문자열의 문자 그대로 포함 여부를 검사하므로 `%`·`_`·역슬래시를
와일드카드로 취급하지 않습니다. 선택한 태그는 정확한 일치이며 최대 20개 결과를 캐시합니다.
정확한 제출과 부분 검색은 현재의 활성·연결 계정 집합을 DB에서 읽은 뒤 JavaScript로 걸러냅니다.
현재 소규모 모임의 정규화 일관성을 위한 선택이며, 계정 수가 크게 늘면 정규화 검색 컬럼 등으로
DB 조회 비용을 줄이는 설계를 검토해야 합니다. 첫 화면의 전적 이동은 부분 검색 캐시가 아닌
`resolveSearchMember()`의 현재 이름·연결 확인을 사용합니다.

키 공간은 `REDIS_KEY_PREFIX`, 배포 환경, PostgreSQL 호스트·DB 이름의 해시와 스키마 버전으로
분리됩니다. 같은 DB를 쓰는 독립 프로젝트는 서로 다른 `REDIS_KEY_PREFIX`를 사용하세요.
같은 프로젝트의 서버 인스턴스는 동일한 prefix를 써야 무효화가 공유됩니다.

## 장애 동작

URL이 없으면 캐시 없이 동작합니다. 연결·명령 대기는 각각 1초로 제한하고 오프라인 명령
큐와 자동 재전송을 사용하지 않습니다. 연결 실패 후 5초간 직접 DB를 사용한 뒤 다시 시도합니다.
경고는 30초마다 최대 한 번 기록하며 URL·비밀번호·원본 오류는 출력하지 않습니다.

조회 실패나 손상된 JSON은 캐시 miss로 처리합니다. 256 KiB를 넘는 결과는 저장하지 않습니다.
캐시 무효화 실패가 이미 완료한 DB 변경을 실패로 돌리지 않습니다. 게시한 캐시 항목의 TTL은
60초이므로 실패한 무효화나 앱 밖의 DB 변경 후 잠시 이전 값·추천이 보일 수 있습니다.
DB와 캐시를 원자적으로 갱신하는 구조는 아닙니다. TTL은 항목 게시 시점부터 계산하므로 느린
조회·재구축이 변경과 겹치면 그 처리 시간까지 포함한 엄격한 ‘변경 후 60초’ 보장은 아닙니다.
자동완성 후보가 잠시 남아 있어도 검색 제출 시 현재 DB 연결과 활성 경기 기록을 다시 확인하므로
연결 해제·삭제된 계정의 오래된 후보만으로 이전 모임원 전적에 이동하지 않습니다.

## Podman 테스트

운영 연결 주소를 테스트 변수에 넣지 않습니다. 테스트는 로컬 루프백 컨테이너만 허용하고,
PostgreSQL 데이터는 실제 마이그레이션을 적용한 메모리 PGlite를 사용합니다.

```bash
podman machine start  # 이미 실행 중이면 생략
podman run --detach --name llvy-redis-test \
  --publish 127.0.0.1:16379:6379 docker.io/library/redis:7-alpine \
  redis-server --save '' --appendonly no
podman exec llvy-redis-test redis-cli INFO server

LLVY_REDIS_TEST_URL="redis://127.0.0.1:16379" npm run test:redis
# Redis 통합 검증을 전체 품질 검사에 포함:
REDIS_URL="" LLVY_REDIS_TEST_URL="redis://127.0.0.1:16379" npm run check

podman rm --force llvy-redis-test
```

이미지의 실제 `redis_version`이 7 계열인지 확인합니다. `test:redis`는 테스트 URL이 없으면
설정 오류로 종료하고, 일반 `npm test`에서는 지정하지 않은 컨테이너 통합 테스트를 건너뜁니다.
테스트마다 UUID 키 공간을 사용하고 해당 키만 제거합니다. `FLUSHDB`나 `FLUSHALL`은 사용하지 않습니다.

## 배포 후 확인

1. 같은 조회를 두 번 수행해 역할별 캐시 키와 TTL을 확인합니다. 다른 서버 인스턴스에서도
   동일한 세대와 결과를 사용하며 변경 후 새 세대로 조회하는지 확인합니다.
2. 일반 사용자 첫 화면에서 한글·영문·이모지 닉네임을 입력하고 최대 10개 접두어 후보를
   확인합니다. NFC·대소문자·`#태그접두어`·키보드 선택·검색 제출을 확인합니다.
3. 정확한 닉네임·태그로 단일 모임원 전적에 이동하고, 태그 없는 동명 계정은 모임원 선택으로,
   없는 닉네임·미연결 계정·제외 경기만 있는 계정은 없는 사용자 안내로 이어지는지 확인합니다.
4. 오너로 조회한 뒤 일반 사용자로 조회해 이름 원문이 표시되고 생년은 일반 사용자 응답과 캐시에
   없는지 확인합니다. 자동완성은 각 후보 DTO의 허용 필드만 반환하고 생년·Discord 정보를 포함하지 않아야 합니다.
   선택 화면 이름은 원문으로 표시되어야 합니다.
5. 자동완성을 먼저 조회한 다음 계정 연결·해제·모임원 삭제·경기 제외·복구를 수행합니다.
   다음 추천이 갱신되고, 이전 후보를 제출해도 현재 연결을 기준으로 처리하는지 확인합니다.
6. 첫 요청·TTL 만료·인덱스 일부 키 제거에서 재구축하고 잘못된 부분 인덱스를 반환하지 않는지
   확인합니다. 재구축이 겹친 요청과 여러 서버 인스턴스의 응답도 확인합니다.
7. 관리자 지정 취소 후 캐시가 있어도 이전 세션의 페이지·자동완성 API 접근이 거부되는지 확인합니다.
8. 별도 Preview에서 연결 실패 시 조회·검색과 데이터 변경이 계속 가능한지 확인합니다.
   무효화 실패 시 남은 TTL 동안 추천이 오래될 수 있음을 확인하고, 제출은 현재 DB 연결을 사용해야 합니다.
9. 검색 읽기만으로 감사로그가 증가하지 않고 로그인·데이터 변경 기록은 유지되는지 확인합니다.

Podman 검증은 명령·캐시와 로컬 데이터 동작의 증거입니다. 실제 Upstash TLS·Vercel 연결 수·
휴면 복귀·네트워크 지연은 이 배포 확인으로 구분합니다. 캐시를 끄려면 URL을 제거하고 재배포합니다.
