# 문서 유지관리

[문서 목록](README.md) · [저장소 지침](../AGENTS.md)

LLVY의 구현 요구사항과 공개 계약은 이 저장소에서 관리한다. 위키는 Worker·업로더 등 부가 프로젝트의 연결 맥락을 설명한다. 아래 표에서 변경의 영향을 받는 항목을 골라 원본부터 갱신한다.

## 변경별 갱신 대상

| ------------------------------- | ------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| API·인증·권한·데이터 동작       | 코드·테스트, 활성 OpenSpec의 proposal·design·specs·tasks, 관련 [구조](architecture.md)·[인증 안내](discord-auth.md) | desktop API는 [계약 정책](../contracts/desktop-v1/README.md)에 따라 서버 원본을 먼저 변경하고 앱의 고정 사본은 별도로 검토한다. 위키의 관련 구조·업로더 요약만 갱신한다. |

아직 없는 API 스키마·fixture·플래그·명령을 문서 갱신을 위해 임의로 만들지 않는다. 구현 전에는 활성 계획을 연결하고 미구현 상태를 유지한다.

## 원본과 확인일

- 현재 동작은 코드·테스트와 대조한다. 계획 변경은 활성 OpenSpec에, 완료한 구현은 필수 검증 후 정식 명세에 반영한다.
- 사실을 재확인한 경우에만 해당 확인일과 근거를 갱신한다. 오탈자·표현 수정은 외부 서비스 검증일을 바꾸지 않는다.
- 검증 기록에는 확인한 대상·명령·결과·범위를 쓴다. 로컬·모의 검사와 실제 외부 서비스·운영 검증을 구분한다.
- 과거 아카이브와 검증 결과를 새 동작으로 덮어쓰지 않는다. 현재 안내를 갱신하고, 과거 기록의 오류 정정이 필요하면 정정 범위를 구분한다.

## 공개 문서에 남길 내용

기술 선택, 결정 이유, 적용 범위, 일반 개발 요건과 재현 가능한 검증 결과를 기록한다. 필요한 Node.js·의존성 버전은 검증 근거가 될 수 있다.
개인 홈 경로·실제 계정 예시·개인 장비 설정·개인 도구 사용 방침·전역 에이전트 지침·대화 및 요청 경위·에이전트 권한 승인이나 샌드박스 해제 과정은 넣지 않는다. 예시는 가상 값과 저장소 상대 경로로 쓴다.

## 완료 전 확인

1. 표에 해당하는 원본·문서를 비교하고 API·기본값·명령·구현 상태가 일치하는지 확인한다. 코드와 명세의 차이를 문구만 바꿔 감추지 않는다.
2. 파일 이동·제목 변경은 기존 경로와 제목을 `rg`로 검색하고 상대 링크·앵커·색인을 확인한다. 외부 사실을 바꾼 경우 공식 근거와 확인일도 확인한다.
3. 변경한 문서의 형식과 후행 공백을 검사한다. `git diff --check`에 잡히지 않는 새 파일도 확인한다. OpenSpec 변경은 `openspec validate --all --strict`와 내용 대조를 수행한다.
4. 개인 정보·개인 환경·대화 경위가 본문·예시·검증 기록에 들어가지 않았는지 검토한다.
5. 중요한 변경은 해당 변경의 검증 기록에 남긴다. 위키를 수정했다면 위키 `log.md`와 영향을 받는 색인도 갱신한다.
6. 연계 저장소를 수정하지 못했으면 대상 저장소·문서 경로·필요한 수정·미완료 이유를 작업 기록과 결과 보고에 남긴다. 로컬 작업은 진행하되 전체 문서 동기화 완료로 보고하지 않는다.

이 절차는 편집·검토 지침이다. 자동 동기화나 CI 링크 검사를 제공하지 않으며, LLVY의 빌드·검증을 위해 형제 저장소를 요구하지 않는다.
